# Система автоматизации — проверяемые сценарии

Актуально на 28 сентября 2026 года. Этот документ фиксирует ожидаемое поведение
приложения. Автоматические тесты используют временную базу,
файлы и имитацию почтового сервера; они не отправляют реальные письма.

## 1. Обязательные проверки до работы с реальными закупками

| ID | Сценарий | Условие прохождения | Проверка |
| --- | --- | --- | --- |
| M1 | Рассылка двум поставщикам | Каждому сформировано отдельное письмо с верным адресом, кодом рассылки и вложениями; повторное нажатие не создаёт вторую рассылку | Автоматическая + живая |
| M2 | SMTP подтвердил отправку одному адресату | Адресат помечен отправленным, сохранены исходное письмо и его `Message-ID`; повторная отправка пропускает адресата | Автоматическая |
| M3 | Соединение оборвалось после передачи письма, до надёжного подтверждения | Адресат получает статус «результат неизвестен»; автоматического повтора нет | Автоматическая + живая имитация сбоя |
| M4 | Ошибка у одного адресата посреди рассылки | Успешные адресаты не отправляются повторно; ошибка и состояние проблемного адресата видны пользователю | Автоматическая |
| I1 | IMAP нашёл несколько UID, один `FETCH` не удался | Курсор синхронизации не перескакивает нескачанное письмо; следующая проверка пробует его снова | Автоматическая |
| I2 | Первичный поиск не нашёл писем | Повторная проверка не перечитывает старый диапазон; письма, появившиеся во время поиска, не пропускаются | Автоматическая |
| I3 | Сервер сменил `UIDVALIDITY` и выдал прежний UID другому письму | Оба письма сохраняются как разные; существующая база переносится без удаления данных | Автоматическая |
| I4 | Сохранение вложений прервалось после первого файла | Следующая проверка завершает обработку; ни один файл не потерян и не учтён дважды; статус не завершён преждевременно | Автоматическая |
| I5 | Повторно пришёл идентичный файл | Копия отмечена как дубль, исходный файл доступен | Автоматическая |
| I6 | Пришёл исправленный файл с тем же именем, но иным содержимым | Обе версии доступны и различимы | Автоматическая |
| I7 | Ответ относится к двум возможным рассылкам | Письмо остаётся на ручную привязку, не назначается молча | Автоматическая |
| I8 | Ответ ссылается на исходное письмо, но отправлен с другого адреса | Письмо сохраняется; правило автоматической или ручной привязки уточняется | Автоматическая |
| I9 | После файла пришёл ответ без вложений | В списке писем новый ответ отмечен «Ответ без файлов», а общий статус поставщика остаётся «Файлы получены» | Автоматическая + визуальная |
| F1 | Файл назван `.pdf`, `.xls` или `.xlsx`, но содержимое другого типа либо повреждено | Файл сохранён для разбора, но не считается пригодным предложением | Автоматическая |
| F2 | Вложение слишком велико или имеет опасное имя Windows | Проверка завершается управляемой ошибкой; остальные письма и база не повреждаются. Численные лимиты уточняются | Автоматическая |
| B1 | Резервная копия создана и затем восстановлена в пустой каталог | База, письма и вложения совпадают с оригиналами; повреждённый архив отвергается до замены рабочих данных | Автоматическая + ручная |

На 24 сентября автоматизированы M2–M4, I1–I4 и I9; также сохранены прежние базовые
проверки справочника, статусов, разбора письма и повторного получения того же
UID. Остальные строки таблицы остаются критериями для следующих циклов работы.

## 2. Живой тест Mail.ru

Использовать отдельный тестовый ящик и минимум два тестовых адреса. Проверить
подключение, русскую тему и текст, исходящие вложения, ответ в цепочку и ответ с
изменённой темой, ответ без файла и с несколькими файлами, перезапуск программы,
временное отсутствие интернета и отозванный пароль приложения. Зафиксировать
фактические результаты и ошибки, не сохраняя пароль в проекте.

Автоматические тесты не заменяют эту проверку: они доказывают логику программы
при заданных ответах сервера, но не поведение живого Mail.ru.

## 3. Генерация сводной по заявке и счетам

Примеры заявки, шести PDF и образца сводной получены 24 сентября. Проверки
ниже выполняются без отправки писем и без обращения к нейросети.

| ID | Сценарий | Условие прохождения |
| --- | --- | --- |
| S1 | Заявка с объединёнными ячейками | Из 19 наименований получаются 29 строк с собственными длиной, количеством и маркой стали; ни одна строка не исчезает |
| S2 | Счёт с текстовым PDF | Извлекаются позиции, масса, цена, сумма, поставщик, номер счёта и страница; сумма строк сверяется с итогом счёта |
| S3 | Счёт за штуки | Цена за тонну появляется только при проверяемой массе (например, кг/м × длина × количество); иначе ставится «масса неизвестна» |
| S4 | Одна позиция у поставщика разбита на партии | Общая сумма и масса складываются; цена за тонну = сумма с НДС / масса в тоннах, а не среднее цен без весов |
| S5 | Разные характеристики | Несовпадение марки, размера или длины видно в результате; такие позиции не считаются точным соответствием |
| S6 | Повтор файла и разные счета | Байтовый дубль не учитывается дважды; разные счета и строки сохраняют источник, даже если товар совпал |
| S7 | Скан PDF | Программа распознаёт текст локально или явно показывает, что документ требует проверки; не выдаёт неполную сводную за готовую |
| S8 | Итоговый XLSX | 29 строк заявки сохраняются; есть блоки поставщиков, средневзвешенные цены, формулы, детализация исходных партий и предупреждения; файл открывается как XLSX |

На предоставленных документах контрольные числа: у ЕВРАЗ для 30Б1 две партии
дают 304 281,60 ₽ / 3,456 т = 88 044,44 ₽/т. Две строки 25К2 в скане
«Металлоторг» дают 2 162 506,50 ₽ / 21,725 т = 99 540 ₽/т, но марка
«С345/С355» требует подтверждения относительно заявки С345.

## 4. Упрощённый интерфейс

| ID | Сценарий | Условие прохождения |
| --- | --- | --- |
| U1 | Основной экран | Пять разделов: «Рассылки», «Требуют внимания», «Поставщики», «Поиск поставщиков», «Настройки»; выбор рассылки показывает её поставщиков и ответы рядом |
| U2 | Создание рассылки | Заявка XLSX выбирается один раз, сохраняется в папке рассылки и прикладывается к отдельным письмам поставщикам |
| U3 | Повторная сводная | Для новой рассылки заявка берётся автоматически; для старой с одним XLSX — также; при неоднозначности требуется выбор файла |
| U4 | Письма на проверку | По умолчанию показаны спорные письма; «Все ответы» показывает остальные; ручная привязка остаётся доступной |
| U5 | Старая база и диагностика | Существующие рассылки остаются после добавления поля заявки; журнал открывается из настроек |

## 5. Поиск поставщиков

| ID | Сценарий | Условие прохождения |
| --- | --- | --- |
| P1 | Запрос по товару и региону | Codex CLI с входом через ChatGPT выполняет веб-поиск; окно приложения остаётся доступным, результат сохраняется как список кандидатов |
| P2 | Контакт без подтверждения | Email или телефон от Codex без ссылки на страницу контактов отбрасывается; компания без контактов остаётся кандидатом |
| P3 | Повторный поиск | Компания с тем же сайтом не создаётся второй раз; категории нового неподтверждённого результата не меняют уже принятую карточку поставщика |
| P4 | Ручная проверка | Пользователь видит источники, может вписать email и телефоны вручную без страницы-источника, отклонить карточку или перенести в справочник; перенос возможен при email или телефоне, поставщик без email не попадает в рассылку |
| P5 | Категории и Excel | Поставщика можно отнести к нескольким категориям и отфильтровать; XLSX содержит категории, источники и статус без исполняемых формул из текста поиска |
| P6 | Отмена или ошибка Codex | Процесс завершается либо сообщает об ошибке; база остаётся доступной, почтовые функции работают |
| P7 | Ответ поставщику | «Ответить» отправляет письмо в цепочке (In-Reply-To/References, «Re:» и номер рассылки, адрес Reply-To) с цитатой и вложениями; ответ виден в переписке, следующее письмо поставщика привязывается к рассылке; отказ сервера помечает ответ как неотправленный |

Локально проверены формат ответа Codex, сохранение кандидатов, дубли, категории,
перенос в справочник, XLSX и запуск интерфейса. Один живой поиск через Codex CLI
вернул две структурированные карточки. Актуальность найденных сайтов, контактов
и ассортимента остаётся предметом проверки пользователя.

## 6. Решения, которые нельзя заменить техническим тестом

1. Можно ли автоматически считать ответ с другого адреса ответом того же поставщика.
2. Нужно ли загружать поздние ответы по завершённой рассылке.
3. Каковы максимальные размеры файла и всего письма.

После согласования этих правил каждый сценарий получает однозначное ожидаемое
поведение и становится проверкой перед выпуском.
