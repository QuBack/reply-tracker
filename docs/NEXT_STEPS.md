# Роза — состояние проекта и план продолжения

Актуально на **24 сентября 2026 года**. План обязательных проверок вынесен в
`TEST_PLAN.md`.

Этот файл — точка входа для продолжения разработки без истории переписки.

## 1. Назначение приложения

Локальное Windows-приложение для одного пользователя и одного ящика Mail.ru.

Рабочий сценарий:

1. Пользователь заводит поставщиков и их email.
2. Создаёт запрос, заполняет тему и текст, прикладывает файлы.
3. Программа отправляет каждому поставщику отдельное письмо.
4. Программа проверяет входящие по кнопке, таймеру и при следующем запуске.
5. Ответ связывается с исходной рассылкой и поставщиком.
6. Все вложения сохраняются; PDF/XLS/XLSX считаются документами предложения.
7. Когда каждый адресат получил конечный статус, запускается подготовка сводного Excel.
8. В дальнейшем на накопленных данных строится статистика поставщиков.

Согласованные правила:

- почта: **Mail.ru**;
- один пользователь и один почтовый ящик;
- одного PDF/XLS/XLSX достаточно для статуса «Файлы получены»;
- если в ответе несколько файлов, сохранять все;
- закрытие окна должно оставлять проверку работающей;
- после полного выхода при следующем запуске проверять незавершённые рассылки.

## 2. Что реализовано

Текущий MVP уже содержит:

- интерфейс на `tkinter/ttk`, семь вкладок;
- SQLite-базу;
- справочник поставщиков;
- форму новой рассылки;
- отдельное письмо каждому поставщику;
- SMTP Mail.ru через SSL/TLS;
- IMAP Mail.ru через SSL/TLS;
- отдельный код рассылки вида `RFQ-2026-0001`;
- сопоставление ответа по `In-Reply-To`/`References`;
- запасное сопоставление по коду в теме;
- запасное сопоставление по адресу отправителя;
- ручную привязку спорного письма;
- ручную проверку почты;
- таймер проверки на 5/10/15/30/60 минут;
- проверку при запуске, если есть активные рассылки;
- сохранение исходного письма в `.eml`;
- сохранение всех именованных вложений;
- признание `.pdf`, `.xls`, `.xlsx` допустимыми документами;
- вычисление SHA-256 и отметку точных дублей;
- статусы адресатов и кампаний;
- ручные статусы «Отказ», «Закрыт без ответа», «Вернуть в ожидание»;
- журнал действий;
- базовые показатели на главном экране;
- ZIP-резервную копию базы, писем и вложений;
- хранение пароля Mail.ru в Windows Credential Manager;
- автоматическую подготовку Tcl/Tk для некоторых установок Python 3.14;
- миграцию старой SQLite-базы с учётом `UIDVALIDITY` у входящих писем;
- защиту от пропуска письма при неудачном IMAP `FETCH` и возобновление обработки
  письма после ошибки сохранения вложения;
- отдельный статус «Исход отправки неизвестен» без автоматического повтора;
- отдельный результат для каждого письма во «Входящих»;
- девятнадцать автоматических тестов.

Генерация сводного XLSX пока намеренно оставлена заглушкой: пользователь должен
передать окончательный промт и требования к таблице.

## 6. Настройка Mail.ru для живого теста

Используются официальные параметры:

- IMAP: `imap.mail.ru:993`, SSL/TLS;
- SMTP: `smtp.mail.ru:465`, SSL/TLS.

Нужен не основной пароль, а отдельный пароль внешнего приложения с полным
доступом к Почте:

<https://help.mail.ru/mail/login/mailer/>

Порядок проверки:

1. Создать пароль внешнего приложения в настройках Mail.ru.
2. Запустить программу.
3. Открыть «Настройки».
4. Ввести полный адрес ящика и пароль приложения.
5. Нажать «Сохранить и проверить».
6. Не передавать пароль разработчику и не записывать его в файлы проекта.

### P0.2. Устойчивость IMAP UID — реализовано, требуется живой тест

Ранее уникальность входящего письма задавалась как:

```text
mailbox + folder + imap_uid
```

Добавлены `uid_validity` в `incoming_messages` и уникальный ключ:

```text
mailbox + folder + uid_validity + imap_uid
```

Причина: после сброса `UIDVALIDITY` сервер может повторно использовать UID.

`UIDNEXT` читается до поиска; при пустом поиске сохраняется `UIDNEXT - 1`.
Если загрузка одного из найденных писем не удалась, курсор не перескакивает его.

Старая база переносится с предварительным снимком `app.db.pre-v2-*.db` рядом с
ней. Версия схемы хранится в SQLite `PRAGMA user_version`. Живой сценарий сброса
`UIDVALIDITY` ещё не проверен.

### 8.3. Не просить модель сразу создавать Excel

Надёжный конвейер:

```text
PDF/XLS/XLSX
    → извлечение текста и таблиц
    → нейросеть возвращает строгий JSON
    → программная валидация JSON
    → ручная проверка спорных строк
    → детерминированная генерация XLSX
```

В JSON для каждой извлечённой позиции должны быть:

- поставщик;
- исходный файл;
- страница PDF или лист/строка Excel;
- исходное название;
- нормализованное название;
- характеристика/марка/ГОСТ/ТУ;
- количество;
- единица измерения;
- цена за единицу;
- сумма;
- НДС;
- валюта;
- срок и условия поставки;
- статус сопоставления с заявкой;
- уверенность;
- предупреждения;
- фрагмент-основание из документа.

### 8.4. Правила итоговой таблицы

При реализации сохранить следующие ограничения:

- исходная заявка задаёт порядок строк;
- не объединять позиции, отличающиеся длиной, размером или количеством;
- не приравнивать единицы измерения без подтверждённого пересчёта;
- точные дубли счетов не учитывать дважды;
- технические аналоги явно отмечать и отправлять на ручную проверку;
- различать цену за единицу и общую сумму строки;
- суммы и итоги в XLSX считать формулами;
- хранить статусы «нет предложения», «аналог», «единица отличается»,
  «неоднозначное соответствие», «требуется ручная проверка»;
- финальный результат должен быть настоящим `.xlsx`, а не текстовым отчётом.

### 8.5. Обработка документов

Потребуются отдельные ветки:

- обычный текстовый PDF;
- скан PDF с OCR;
- современный XLSX;
- старый бинарный XLS;
- многостраничный счёт;
- несколько счетов в одном ответе;
- один и тот же счёт в PDF и Excel;
- защищённый или повреждённый файл.

После генерации XLSX обязательно проверить:

- открытие файла;
- формулы;
- числа и валюты;
- объединённые ячейки;
- ширину столбцов и перенос текста;
- закрепление областей;
- фильтры;
- печатный вид;
- отсутствие скрытых ошибок Excel.

## 14. Критерии готовности версии 1.0

  программа останавливает автоматический повтор и показывает этот статус.
- Ответы корректно догружаются после перезапуска.
- PDF/XLS/XLSX не теряются и не учитываются дважды.
- Неоднозначные ответы не привязываются молча к неправильной рассылке.
- Ошибки сети не портят базу и доступны в журнале.
- Резервная копия реально восстанавливается.
- Нейросеть возвращает проверяемые данные с указанием источника.
- Пользователь может исправить спорные соответствия до генерации.
- Итоговый XLSX открывается и содержит формулы, предупреждения и исходный порядок
  заявки.
- Приложение устанавливается и работает на чистом Windows без Python.
